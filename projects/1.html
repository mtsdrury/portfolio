Fern: Persistent Foraging RPG for Discord

Multi-area progression RPG bot with energy systems and cross-bot economy integration

View Repository →
Python discord.py Supabase PostgreSQL JSON

The Problem

Discord communities need engaging, persistent gameplay that encourages regular participation without forcing synchronous interaction. Existing bot games reset progress or lack depth, failing to maintain long-term engagement. A resource-gathering RPG system with unlockable areas, tool progression, and cross-bot economy integration solves this by giving users meaningful progression tied to their activity over time.

What Was Built

  • The Fern bot implements a foraging RPG with four distinct activities: gathering, chopping, mining, and fishing, each tied to specific areas and tool tiers defined in `fern_items.py` and `fern_items_nofishing.py`.
  • Energy management limits sessions per day. Users start with 5 max energy, recoverable through sleep mechanics tracked via `sleep_until` timestamps in `foraging_data` table.
  • Progression unlocks new areas (tracked in `unlocked_areas` JSON array) and tool upgrades through a tiered system. `tool_tiers` column stores axe, pickaxe, and fishing rod levels per user.
  • The bot integrates with Sterling (the main economy bot) through a shared Supabase backend. Bones earned in Fern sync to `user_bones` table, allowing cross-bot purchasing and inventory management.
  • Session state persists across crashes using `active_session` and `last_session` JSON fields, enabling recovery of in-progress expeditions.
  • Migration scripts (`migrate_foraging_to_database.py`) transition legacy JSON storage to Postgres while maintaining backward compatibility during rollout.
  • Database schema (`foraging_database_schema.sql`) separates user progression, inventory items, and fish catch history into normalized tables with RLS policies.
  • Onboarding flow (`onboarded` flag and `seen_tool_intros`) introduces mechanics gradually, showing tutorials for each tool type on first use.

Outcome

The system supports persistent multi-area progression with energy-based pacing, tool upgrades, and a shared economy. Both bots run concurrently, with Fern handling gathering mechanics and Sterling managing broader economy features like shops, stocks, and achievements. Migration tooling enables live transition from JSON to Supabase without downtime.

Highlights

Cross-bot economy sync

Fern and Sterling share a single Supabase backend for user balances and inventory. Bones earned through foraging immediately become spendable in Sterling's shop system. The `user_bones` and `user_inventory` tables serve both bots, with filelock-based concurrency control preventing race conditions during simultaneous writes.

Stateful session recovery

Active foraging sessions serialize to `active_session` JSON column, storing current area, tool tier, gathered items, and energy spent. Bot restarts check for unfinished sessions on user interaction and present recovery prompts. The `expedition_log` field preserves multi-stage expedition state across async interactions.

Tiered progression gating

Areas unlock based on foraging level and tool tiers. The `unlocked_areas` array gates access to higher-value regions like cliffs or caves. Tool upgrades in `tool_tiers` directly affect loot tables defined in `foraging_tools.json`, `chopping_tools.json`, and `mining_tools.json`. Blacksmith and fisherman NPCs unlock at specific milestones, stored as boolean flags.

Zero-downtime data migration

The migration script (`migrate_foraging_to_database.py`) reads existing `fern_data.json`, transforms nested structures, and bulk inserts to Postgres. A sync script (`sync_json_from_database.py`) maintains JSON fallback during transition. This dual-write approach allows rolling back to JSON if database issues occur, with eventual consistency handled through timestamp comparison.
