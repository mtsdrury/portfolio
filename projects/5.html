Text-to-SQL Evaluation Pipeline

Systematic benchmark of open-source LLMs on text-to-SQL generation across difficulty tiers

The Problem

Text-to-SQL generation remains an open challenge in NLP. While proprietary models are often benchmarked, the performance characteristics of open-source LLMs across different SQL complexity levels are less documented. Teams evaluating model deployment need quantitative data on execution reliability, accuracy degradation patterns, and failure modes to make informed decisions about which models can handle production workloads.

What Was Built

  • Built a 18-query benchmark spanning 5 difficulty tiers (basic aggregations, multi-table joins, window functions, CTEs, complex combinations) using the Chinook music store database
  • Implemented `query_runner.py` with order-insensitive result comparison, float normalization to 2 decimal places, and detailed failure mode classification (execution error, wrong row count, wrong values)
  • Created `llm_generator.py` with HuggingFace Inference API integration, retry logic with exponential backoff, and regex-based SQL extraction that handles markdown code fences and mixed text/SQL output
  • The evaluation pipeline (`evaluate.py`) runs 4 models across all queries with incremental resume support, storing results in structured JSON with per-concept breakdowns
  • Added a FastAPI layer (`api/main.py`, `routes/generate.py`) that exposes single-question generation as an interactive playground, separate from batch evaluation
  • Containerized with Docker Compose, mounting results volume for persistence and reading HuggingFace tokens from environment variables
  • Built Jupyter notebook (`analysis.ipynb`) with seaborn visualizations for execution rate, accuracy by difficulty tier, failure mode distributions, and latency comparisons

Outcome

The system completed evaluation of 4 models (Qwen2.5-Coder-32B, Qwen2.5-Coder-7B, Mistral-7B, Llama-3.1-8B) across 72 total inference calls. Results show clear degradation patterns as SQL complexity increases, with the 32B model achieving 44% accuracy overall but dropping to 0% on complex combinations. The API provides a working playground for ad-hoc exploration, while the batch pipeline and visualizations offer reproducible benchmarking infrastructure.

Highlights

Order-insensitive result comparison

The comparison logic in `query_runner.py` converts result sets to normalized tuples (floats rounded to 2 decimals) and compares as sets, so equivalent queries with different ORDER BY clauses still match. This avoids false negatives from semantically identical results with different orderings.

Incremental resume for long evaluations

The batch pipeline checks `evaluation_results.json` before each inference call and skips already-completed model/query pairs. This allows 72-call evaluations to resume after API rate limits or transient failures without re-running successful queries.

Failure mode taxonomy

Every failed query is classified into execution_error (malformed SQL), wrong_row_count (partial results), or wrong_values (incorrect aggregates/joins). The Jupyter notebook breaks down failure distributions by model, revealing that Llama-3.1-8B produces 10 execution errors while the Qwen models mostly fail on wrong values.

Dual CLI and API architecture

Batch evaluation runs from `src/evaluate.py` with progress tracking and JSON output. The FastAPI layer in `api/` serves the same generation engine via POST /api/generate with optional ground truth comparison, targeting different use cases without coupling the two execution paths.

Results

Model accuracy and execution reliability

Qwen2.5-Coder-32B achieves 44.4% exact match accuracy with 94.4% execution success, nearly doubling the accuracy of its 7B counterpart (22.2%). Mistral-7B reaches 27.8% accuracy while Llama-3.1-8B drops to 5.6% with only 44.4% of queries executing without SQL errors.

Metrics: 32B model: 44.4% accuracy, 94.4% exec | 7B models: 22-28% accuracy, 89% exec | Llama-3.1: 5.6% accuracy, 44% exec

Difficulty tier performance degradation

The 32B model scores 67% on basic and intermediate queries, peaks at 75% on window functions, drops to 25% on CTEs, and falls to 0% on complex combinations. All models fail to solve any complex-tier query, showing a consistent accuracy cliff as SQL patterns stack.

Metrics: 32B: Basic 67%, Window 75%, CTE 25%, Complex 0% | 7B models: Basic 67%, everything else ≤33%

Failure mode distribution by model

Llama-3.1-8B produces 10 execution errors (malformed SQL), while Qwen and Mistral models generate syntactically valid queries that mostly fail on wrong values (semantic errors in joins or aggregates). Mistral shows 4 wrong row count failures, indicating partial result sets.

Metrics: Llama: 10 exec errors | Mistral: 7 wrong values, 4 wrong row counts | Qwen-32B: 8 wrong values, 1 exec error

Inference latency characteristics

Qwen2.5-Coder-32B shows median latency around 1.2 seconds with outliers up to 5 seconds. The 7B models cluster between 1-2.5 seconds. Llama-3.1-8B exhibits the lowest latency (0.3-0.4s median) but with an 8-second outlier, reflecting its lower execution success rate and frequent early failures.

Metrics: 32B median: 1.2s | 7B median: 1.5-2.0s | Llama median: 0.35s
